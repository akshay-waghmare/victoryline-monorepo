# Feature Specification: Full Angular SSR Migration

**Feature Branch**: `012-full-angular-ssr`  
**Created**: 2026-05-18  
**Status**: Draft  
**Input**: User description: "repo here does not have a proper angular SSR, which is affecting SEO and it is not working properly; convert this sidecar type SEO architecture to a full SSR; use speckit and plan spec and task generate for this"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Search Crawlers Receive Rendered Angular Pages (Priority: P1)

As a search crawler, I need every public Angular route to return fully rendered HTML from the application server, not a bot-only prerender sidecar snapshot, so page content, titles, descriptions, canonicals, and structured data are visible without client-side JavaScript execution.

**Why this priority**: This is the core SEO failure in the current architecture. The existing setup serves static Angular for users and sidecar-generated snapshots for selected bots/routes, which is incomplete and stale.

**Independent Test**: Build the frontend SSR bundle, start the SSR server, and request `/`, `/matches`, and `/cric-live/{slug}` with a normal user agent and a bot user agent. Both must receive server-rendered HTML from the same Angular SSR path.

**Acceptance Scenarios**:

1. **Given** the SSR frontend is running, **When** Googlebot requests `/matches`, **Then** the response contains Angular-rendered page content and SEO tags without using `/prerender/*`.
2. **Given** the SSR frontend is running, **When** a normal browser requests `/cric-live/{slug}`, **Then** the initial response is also server-rendered and then bootstraps the same Angular app on the client.
3. **Given** a route is not an API/static asset route, **When** it is requested directly, **Then** Express uses Angular Universal to render `index.html` for that route.

---

### User Story 2 - Live Match SEO Uses Fresh Backend Data During SSR (Priority: P1)

As a cricket search user, I need live match pages to include current team names, match status, canonical URL, and structured data in the initial HTML so search results and social previews stay accurate.

**Why this priority**: Live match pages are the highest SEO-value pages and current sidecar prerendering can be stale, partial, or missing for newly discovered matches.

**Independent Test**: Request a live match URL through the SSR server with backend reachable and verify the response includes match-specific title/meta content generated by Angular/server-side data fetching.

**Acceptance Scenarios**:

1. **Given** backend live match APIs are reachable, **When** `/cric-live/{slug}` is SSR-rendered, **Then** server-side HTTP requests use backend service URLs instead of browser-relative `/api/*` URLs.
2. **Given** backend data changes, **When** the route is requested again after cache expiry, **Then** the SSR response reflects the current backend data instead of an old prerender file.
3. **Given** backend APIs are temporarily unavailable, **When** SSR rendering fails for a route, **Then** the server logs the render error and returns the Angular shell rather than a sidecar 404.

---

### User Story 3 - Deployment Runs One SSR Frontend Service (Priority: P2)

As an operator, I need the frontend container and reverse proxy to run the Node SSR server directly, without the prerender sidecar or Nginx bot-detection rules, so deployment is simpler and SEO behavior is consistent.

**Why this priority**: Removing the sidecar avoids route drift, stale generated files, and bot/user HTML mismatches.

**Independent Test**: Build the Docker image and inspect compose/Caddy wiring to confirm traffic routes to the SSR server port and no runtime dependency on the prerender sidecar remains for the frontend.

**Acceptance Scenarios**:

1. **Given** the frontend image starts, **When** `/health` is requested, **Then** it reports the SSR service as healthy.
2. **Given** Caddy proxies to the frontend, **When** any public route is requested, **Then** traffic reaches the SSR server, not Nginx static routing.
3. **Given** API, sitemap, robots, and WebSocket routes are requested, **When** they pass through the edge/frontend stack, **Then** existing backend proxy behavior remains compatible.

---

### Edge Cases

- Server rendering must not crash when browser-only APIs such as `window`, `document`, `localStorage`, `sessionStorage`, `matchMedia`, `requestAnimationFrame`, or WebSocket clients are unavailable.
- Relative Angular HTTP requests must be rewritten to backend URLs only during SSR; browser requests must remain relative so existing proxy behavior continues.
- Static assets with hashed filenames must be served directly with long cache headers and must not go through Angular rendering.
- API and WebSocket routes must not be captured by Angular route fallback.
- Existing sitemap/robots backend endpoints must remain accessible from the public host.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The frontend MUST use Angular Universal to render Angular routes server-side.
- **FR-002**: The frontend MUST remove runtime dependence on the prerender sidecar for SEO HTML delivery.
- **FR-003**: The SSR server MUST serve static Angular assets and route all non-asset public page requests through Angular Universal.
- **FR-004**: The SSR server MUST preserve existing backend proxy behavior for `/api/*`, `/api/v1/*`, `/token/*`, `/robots.txt`, `/sitemap.xml`, `/sitemaps/*`, and WebSocket traffic.
- **FR-005**: Angular server rendering MUST guard browser-only APIs so SSR does not fail before rendering public pages.
- **FR-006**: Server-side Angular HTTP requests to `/api/*` MUST resolve to the backend service URL during SSR.
- **FR-007**: The Docker frontend image MUST run the Node SSR server rather than Nginx prerender routing.
- **FR-008**: Compose and Caddy configuration MUST route frontend traffic to the SSR server port.
- **FR-009**: The SSR server MUST provide a `/health` endpoint suitable for container health checks.
- **FR-010**: SSR failures MUST be logged and must not return a sidecar-specific 404 for public Angular routes.

### Key Entities

- **SSR Render Request**: A public page request handled by Express and Angular Universal, with route, headers, canonical host context, and render outcome.
- **Backend Proxy Route**: A non-page request that must be forwarded to the Spring backend or scraper without Angular rendering.
- **Browser Capability Guard**: A code path that detects server vs browser execution before using DOM, storage, media, animation, or WebSocket APIs.
- **SSR Deployment Target**: The frontend container/runtime that exposes the Node SSR port and serves both rendered HTML and static assets.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `npm run build:ssr` completes successfully in `apps\frontend`.
- **SC-002**: `npm run ssr:start` serves `/`, `/matches`, and `/cric-live/{slug}` with HTTP 200 from the SSR server.
- **SC-003**: The frontend Dockerfile no longer executes `npm run prerender` or serves `/prerender/*` via Nginx.
- **SC-004**: Docker/Caddy configuration references the SSR server port for frontend traffic.
- **SC-005**: SSR route requests do not throw `window is not defined`, `document is not defined`, `localStorage is not defined`, or `sessionStorage is not defined`.
